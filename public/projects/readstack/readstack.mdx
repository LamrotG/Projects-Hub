# Overview

ReadStack is a full-stack reading habit tracker designed to help users move from simply saving content to actually completing it.

The application consolidates reading management into a single workflow where users can capture, organize, track, and reflect on content such as articles, books, and posts.

Rather than acting as a passive bookmark system, ReadStack focuses on structured progression and habit formation over time.

---

# Background

Most reading tools prioritize saving content over completing it. As a result, users accumulate large collections of unread material without a clear system for follow-through.

ReadStack was created to solve this fragmentation by combining saving, tracking, and review into a unified experience.

---

# Problem

Existing reading workflows suffer from:

* fragmented saving and tracking systems
* lack of structured reading progression
* poor visibility into reading habits
* minimal feedback loops for completion
* high friction between saving and actual reading

These issues result in low completion rates and inconsistent reading habits.

---

# Objectives

The project was designed with the following objectives:

* Provide a fast way to capture reading items into a personal queue
* Track lifecycle stages: Pile → Active → Paused → Done → Archived
* Support weekly reading goals and check-ins
* Enable post-reading notes and reflections
* Maintain a lightweight, distraction-free interface

---

# Solution

ReadStack implements a unified system where all reading activity is managed in one place.

Users can:

* add items to a reading pile
* move items through structured reading states
* track progress over time
* log check-ins and goals
* reflect on completed items

The system emphasizes continuity between saving and completing content.

# Architecture

## System Design

The application is split into two services:

* **Client** — React SPA built with Vite, deployed on Vercel with client-side routing
* **Server** — Node.js/Express REST API deployed on Render handling authentication, business logic, and data access

The system uses PostgreSQL (Neon) as the primary database with SSL-based connections.

---

## Data Flow

1. User authentication generates a JWT on the server
2. Client stores token in localStorage
3. Token is attached to every request via Authorization header
4. Server middleware validates token from cookie or header fallback
5. Protected routes enforce authentication before executing business logic

---

# Technical Decisions

**Authorization header over cookies in production**  
Cross-origin restrictions between Vercel and Render make cookie-based authentication unreliable. The system uses JWT tokens stored in localStorage and passed via Authorization headers. Cookies are retained only for local development compatibility.

**Promise.allSettled for dashboard loading**  
Dashboard data is fetched in parallel. Using Promise.allSettled ensures that partial failures do not block rendering of the entire interface.

**ESM-based backend structure**  
The backend uses ES modules with migration tooling adapted for compatibility across environments.

**Stable date handling strategy**  
Database date fields are normalized into consistent string formats to avoid timezone inconsistencies in API responses.

# Engineering Challenges

## Cross-Origin Authentication

The original cookie-based authentication approach failed in production due to browser restrictions on third-party cookies.

The system was redesigned to use token-based authentication via Authorization headers, ensuring compatibility across separated frontend and backend deployments.

---

## Resilient Data Loading

Dashboard loading initially failed when individual endpoints timed out or errored.

This was resolved by introducing partial failure tolerance using Promise.allSettled, allowing the UI to render available data instead of failing completely.

---

# Lessons Learned

* Cross-origin authentication must be designed explicitly for production environments
* Dashboard systems should tolerate partial data failure
* Environment variables behave differently at build time vs runtime
* Production constraints often differ significantly from local development assumptions
