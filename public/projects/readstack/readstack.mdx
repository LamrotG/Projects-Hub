# Background

Most reading tools focus on saving content rather than completing it. Saved links accumulate without structure, and users often lose track of what they intended to read. ReadStack was built to address this gap by focusing on progression rather than storage.

---

# Problem

Users consistently save more content than they consume. Existing tools separate saving, tracking, and reviewing into different systems, creating friction that reduces follow-through. There is no unified workflow that connects saving content with active reading progress and reflection.

---

# Objectives

*Provide a fast way to capture reading items into a personal queue
*Track lifecycle stages: Pile → Active → Paused → Done → Archived
*Support weekly reading goals and check-ins
*Enable post-reading notes and reflections
*Maintain a lightweight and distraction-free interface

---

# Solution

ReadStack is a full-stack web application built with a React frontend and Node.js/Express backend, connected to a PostgreSQL database on Neon. It unifies saving, tracking, and reviewing reading activity in a single workflow where items progress through structured states.

---

# Key Features

## Reading Pile System

-A compact input system allows users to quickly add reading items. Entries expand only when needed, supporting structured metadata capture. URL-based items automatically extract metadata to reduce manual input.
-Dashboard and Reading Lifecycle
-Items are organized into structured states (Pile, Active, Done, Archived). Each item can be updated through a detailed modal interface with both manual actions and automatic state-saving behavior.

---

## Profile and Settings

Users can manage account settings including display preferences, authentication details, and UI customization. Changes are reflected immediately using optimistic updates.

# Architecture

## System Design

The application is split into two services:

Client — React SPA built with Vite, deployed on Vercel with client-side routing
Server — Node.js/Express REST API deployed on Render handling authentication, business logic, and data access

The system uses PostgreSQL (Neon) as the primary database with SSL-based connections.

---

## Data Flow

User authentication generates a JWT on the server
Client stores token in localStorage
Token is sent via Authorization header on all requests
Server middleware validates token from cookie or header
Protected routes enforce authentication before executing business logic
Technical Decisions

Authorization header over cookies in production
Cross-origin restrictions between Vercel and Render prevent reliable cookie-based authentication. The system uses JWT tokens stored in localStorage and sent via Authorization headers. Cookies are retained only for local development compatibility.

- Promise.allSettled for data fetching
Dashboard data is loaded in parallel. Using Promise.allSettled ensures partial failures do not block rendering of the entire interface.

- ESM-based backend structure
The server uses ES modules with migration tooling adapted for compatibility, ensuring consistency across development and production environments.

- Stable date handling strategy
Database date fields are normalized into consistent string formats to avoid timezone-related inconsistencies in API responses.

# Engineering Challenges

Cross-Origin Authentication

The system initially used cookie-based authentication, which failed in production due to browser restrictions on third-party cookies. The architecture was adapted to use token-based authentication with Authorization headers, ensuring compatibility across separate frontend and backend deployments.

Resilient Data Loading

Dashboard data fetching was redesigned to prevent full UI failure when individual endpoints fail or time out. This was solved by introducing partial result handling across parallel requests.

---

# Lessons Learned

* Cross-origin authentication requires explicit design decisions early in architecture
* Dashboard systems should tolerate partial data failure instead of blocking entirely
* Environment variable behavior differs significantly between build time and runtime
* Deployment environments introduce constraints that do not appear in local development

# Reflection

ReadStack demonstrates the importance of aligning system design with real-world deployment constraints. The transition from local development assumptions (such as cookie-based auth) to production-safe architecture (token-based authentication) resulted in a more portable and scalable system.

The project also reinforced the value of resilience in UI data loading and the importance of designing systems that degrade gracefully rather than failing completely under partial service failure.
